# 加固 APK／SO 调试实战经验

## 8. 实战补充：BlueStacks 上的 GDB 加固样本调试

整理日期：2026-09-15。基于小八桌面 2.7.3 与小八智控大师 1.6.3 的实际分析。本节记录已经做过的操作、失败原因与可复核结果；不将这些现象推广为所有 360 加固版本的统一行为。

本次目标是回答业务接口问题：原车底栏如何处理、方向盘事件从哪里来、如何转为音乐控制。有效路线是：静态筛查 → 限定进程的退出定位 → 预热 GDB 并选择附加时机 → 导出结构合法的运行时 DEX → 反编译和交叉核对。没有先重建一份可重新运行的完整 SO。

### 8.1 环境和可核对结果

| 项目 | 小八桌面 | 小八智控大师 |
| --- | --- | --- |
| 应用版本 | 2.7.3 / versionCode 207399 | 1.6.3 / versionCode 33 |
| 原 APK SHA-256 | 25effcacd74d56c3941adc2e44022ede75cf0f3de838ee56901d762bae1240ba | 9ace0d266b737fcde0696850924b3287523f41daa6c8b9f1e491239abcb30570 |
| 主要可读业务 DEX | 8,858,712 字节 / 4,756 个类 | 9,163,916 字节 / 5,454 个类 |
| JADX 结果 | 部分业务可读，报告 22 项错误 | 部分业务可读，报告 32 项错误 |
| 验证边界 | 取得客户端代码；未完成实车接口验证 | 取得按键和媒体控制代码；未收到真实方向盘事件 |

共同环境：macOS、BlueStacks Air、Android 13 / API 33、arm64-v8a；GNU GDB 16.3（aarch64-linux-android）、JADX 1.5.6。显示配置为 1920 × 1080 px、320 dpi。模拟器已有可用的 root 调试入口；未修改 SELinux 或系统分区。

GDB 及依赖取自 Termux 仓库，按 HTTPS 仓库索引中的 SHA-256 逐项校验，仅解包到任务临时目录运行，没有执行软件包安装脚本。普通未 root 的 release 应用不一定允许附加，必须先检查目标环境，不能照抄此条件。

### 8.2 先筛查样本，再决定是否需要动态分析

- 保存原包并记录版本、包名、ABI、文件 SHA-256 和签名证书；重复下载先比对哈希。签名校验成功说明包内签名一致，不单独证明发布者身份或软件行为。
- 静态解包仍有价值：Manifest 可定位启动 Activity、服务、权限和包可见性；布局资源可定位界面功能与尺寸常量。
- 本次出现 StubApp、libjiagu 和少量壳类，说明普通静态 JADX 未恢复业务代码。字符串搜索无结果只能说明当前可见层没有线索，不能证明功能不存在。
- 只跟进与目标有关的类和调用链。运行时恢复出业务 DEX 后，先分析它；只有需要 native 算法或重新加载 SO 时，才继续 ELF 重建路线。

### 8.3 退出原因：从系统记录走到实际调用

先用目标包的进程退出记录与限定日志确认症状。ApplicationExitInfo 中的 SIGNALED / status 9 只能说明收到 SIGKILL，不能仅凭这一项判定是系统回收、反调试、授权失败或车辆信息缺失。

限定目标进程的 strace 捕获到了 kill(selfPid, SIGKILL)；GDB 随后截停 kill / tgkill 系统调用并读取参数、调用方地址和映射。由此能确认：在这次跟踪条件下，终止是目标进程内部代码触发的。

启动日志曾出现 CoreComponentFactory 类找不到，但后续仍有业务初始化和 Activity 跳转。不能把第一条醒目的错误当作根因。GDB 和 strace 本身也可能触发保护；带调试与不带调试的行为必须分别记录。

```text
# 仅示意已附加进程后的观察设置；系统调用编号针对 AArch64 Linux。
set pagination off
set print frame-arguments none
set auto-load off
set debuginfod enabled off
catch syscall 129 130 131
continue

# 截停后检查，而不是把每一次 kill 调用都当成退出：
info registers pc lr x0 x1 x2
bt 20
info proc mappings
x/16i $pc-16
```

AArch64 Linux 上，本次使用的 129 / 130 / 131 分别对应 kill / tkill / tgkill。kill、tkill 的信号参数为 x1，tgkill 的信号参数为 x2。先确认目标 PID／线程与信号参数确实为 9；其他架构不能复用这些编号和寄存器约定。

### 8.4 最关键的经验：预热调试器，避开取样时机竞态

| 现象 | 本次判断 | 有效调整 |
| --- | --- | --- |
| ptrace: No such process | 发现 PID 后才启动 GDB，GDB 尚未就绪，应用已退出 | 先启动 GDB，再启动目标应用 |
| 附加成功但没有可读业务 DEX | 暂停得过早，运行时还原尚未到达目标阶段 | 让初始化推进后再附加，不能据此断言 Dump 无效 |
| 目标未启动 / 等待超时 | 把调试器启动、应用启动分成多个交互步骤，人工或工具调度间隔超出等待窗口 | 由同一编排程序监听就绪标记并立即启动应用 |
| SIGSTOP 再次使批处理停住 | 为抢早期 PID 主动暂停进程，线程组还留有此次暂停产生的信号 | 核对并处理自己引入的暂停状态；优先采用预热后附加 |

智控大师最终成功的顺序：GDB 先启动 → 输出 DEBUGGER_READY → 主机编排器立即请求启动目标 Activity → GDB 发现目标 PID → 等待约 650ms → attach → 在终止调用处读取 DEX。650ms 只是这份样本、这次环境的测得窗口，不是通用解壳时间。

```text
GDB ready
  → 启动目标 Activity
  → 等待目标 PID 出现
  → 按已测得的窗口附加
  → 验证当前执行位置和内存状态
  → 导出本次需要的数据
  → detach 并结束测试
```

需要给整个流程设超时、目标包校验和失败清理。不要用无限重启碰运气；每次重试必须对应新的证据或取样策略。调试器对 ART 使用的信号如何处理也要有目的，不能通用地忽略真实 SIGSEGV。

### 8.5 如何确认匿名执行区域与 .bss 的关系

本次调用方地址落在标为 [anon:.bss] 的可执行映射中，且邻接 libjiagu_64.so。确认归属时又读取了原始 ELF 的 PT_LOAD，将运行时地址换算回该库加载段的内存范围，而不是只看 maps 中的名字或相邻关系。

```text
ELF 虚拟地址 = 运行时地址 − load_bias
加载段内存范围 = [p_vaddr, p_vaddr + p_memsz)
文件已有字节范围 = [p_vaddr, p_vaddr + p_filesz)
```

小八桌面样本的一个调用方相对首个映射为 +0x21d974；该样本首个 PT_LOAD 的虚拟地址为 0，因而可结合加载段范围定位到加固库的内存扩展区。不能把“首个映射起点”无条件当作所有 ELF 的 load_bias，换算需要核对对应段和页对齐。

仅落在该区域，能支持“这次调用来自加固库加载范围中的代码”；不能自动恢复出原始业务函数名。遇到 ?? 或回溯中止时，应报告可确认的模块和偏移，不给无法解析的帧起一个推测名称。

mmap / mprotect 和权限变化可以作为辅助观察点，但并非所有样本都会在“全部解密完成”之后调用一次 mprotect；已有可执行映射、分段解密或 VMP 都会改变观察结果。本次成功流程没有依赖这个假定。

### 8.6 DEX 导出的验证标准

- 只对目标进程的限定可读区域做候选搜索，设置区域及总读取量上限；本次保留的是通过结构检查的 DEX 容器，不是任意堆内存镜像。
- 检查 magic、header_size、endian_tag、file_size，以及 string / type / proto / field / method / class 索引表是否落在文件范围内。结构合法只是初筛，还要检查实际类名、字符串和指令是否有意义。
- 如果魔数被擦除，只有在其他结构证据充分时才尝试恢复“供读取的容器头”，并在记录中注明。这不等于恢复原始文件，也不修改运行中的应用。
- 每个候选独立计算哈希。同尺寸不等于同内容；智控大师取得的两个同尺寸业务容器有大量字节不同，其中可读性也不同。
- JADX 能退出、能显示类名、能恢复某个方法、整个应用能重新运行，是不同层级的结果。复杂 Kotlin、混淆代码和 native 方法仍可能无法完整恢复。
- 先围绕目标核对简单方法、接口描述符、参数写入顺序和回调去向。发现互相矛盾的分支、非法类型表达式或重复代码时，标明反编译不确定性，必要时回到指令或运行时证据。

### 8.7 工具与打包中实际遇到的问题

| 问题 | 经验 |
| --- | --- |
| GDB 运行环境不匹配 | 使用与目标 ABI 匹配的 Android 构建。解包后按需设置 LD_LIBRARY_PATH、PYTHONHOME 等，先验证 gdb --version 和 Python 支持。 |
| macOS tar 带入 AppleDouble 文件 | ._*.py 会污染 GDB Python 模块扫描；本次出现 gdb.function. 等导入错误。打包时关闭资源叉复制并排除 ._*。 |
| macOS ar 无法按列出的名字提取 deb 成员 | 本次改为解析 ar 成员头取得 data.tar，再按安全解包规则处理；未执行控制脚本，未因工具差异误判包损坏。 |
| run-as 返回 setegid 失败 | 这是访问方式失败，不等于包未安装、凭证不存在或业务代码不存在。分析权限另行确认。 |
| MiniDebugInfo / section 警告很多 | 不单凭警告数量判断附加失败；检查是否有目标线程、有效寄存器、实际 catchpoint 和可读映射。 |
| 缺少 syscall XML | 本次使用明确的架构对应编号仍成功截停，但失去名称展示和编号校验，报告中注明这一限制。 |

```bash
# 打包自己准备的临时运行环境，避免 macOS 附加文件污染。
COPYFILE_DISABLE=1 tar -czf gdb-runtime.tgz \
  --exclude='._*' -C runtime/usr .
```

### 8.8 三个业务发现，说明为什么要回到具体问题

- VIN：恢复出的客户端明确调用 ECARX Device.create(context).getVin()，同时有 Android ID 降级。此前“没有 VIN 就必然不能启动”的推断不能成立。
- 原车底栏：小八自己的高度来自 100 / 112 / 124 / 136dp 四档配置；原车栏走显隐控制。取得代码后仍没有证据把 112dp 当作领克原车底栏高度。
- 方向盘：智控大师的主链路是 OneOS Binder 回调，部分键由限定系统日志补充，再做去重、单双长按识别和媒体命令分发。这修正了仅凭桌面切歌函数推测方控实现的做法。

客户端存在某个调用，不等于车机服务允许任意应用使用。此次还发现了试探多个 Binder 事务号的实现；它是样本行为，不能作为稳定的厂商 API 契约直接移植。模拟器中没有目标车机服务时，只能确认客户端链路，不能宣称实车接口或物理按键已跑通。

### 8.9 交付与清理

- 保留原 APK 和哈希；将结构化导出、反编译结果、实际触发条件、成功／失败尝试记录在本地隔离目录。
- 对外知识文档只放经核对的步骤、最小接口证据和限制。不上传完整内存、第三方源码、Cookie、Token、真实 VIN、Android ID、账号标识或个人绝对路径。
- 结束前确认 GDB 已 detach、目标测试进程已停止，删除本任务设备端临时调试目录；不要用宽泛进程名清理其他人的调试会话。
- 按测试前记录核对显示和权限状态。ADB 是否保持开启遵循用户要求；不要把模拟器清理操作套用到实车系统组件。

本次最终状态：两份原包均取得了有用的客户端代码；没有修复并重新发布第三方 SO，没有改变授权检查，也没有完成实车 VIN、底栏或方向盘验证。对于已经能从 DEX 回答的问题，没有继续追求“完整脱壳可运行 APK”。
