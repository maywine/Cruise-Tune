# OneOS 方向盘按键适配

目标环境为领克 01 / LYNK OS N。当前客户端使用 Binder 协议，随 0.5.29 发布；厂商服务权限与物理按键回调需在目标固件上确认。

## 使用和诊断

入口为「设置 → 方向盘按键」。默认关闭厂商适配，标准 Android 媒体键仍由 Media3 处理。

停车后开启「启用 OneOS 车机适配」。需要排查时开启「诊断模式（不执行映射）」：它记录按键、附加参数、调用 UID、计数与菜单状态，不执行自定义映射，也不阻断原有系统媒体键。即使菜单未知，已经到达的 OneOS 事件仍会显示。

按一次播放／左右键后点击「复制诊断信息」，可得到最近 32 条受限记录；不读取账号、VIN、Android ID、音乐目录或全量系统日志。报告区分服务查找、绑定、输入服务发现、监听提交、真实事件和菜单查询。重复按同一键会增加次数，避免看起来毫无变化。「重新连接车机按键」会重建连接；关闭开关后保留当前界面诊断供复制。

| 来源码 | 映射键 | 默认单击 | 默认双击／长按 |
| --- | --- | --- | --- |
| 200085、85 | 播放键 | 播放／暂停 | 不执行 |
| 200088 | 左键 | 上一首 | 不执行 |
| 200087 | 右键 | 下一首 | 不执行 |

单击、双击、长按都可分别改为不执行、播放／暂停、上一首、下一首、播放、暂停。配置保存在本地。

## 协议与适用范围

协议实现位于 [OneOsContract.kt](../android-app/app/src/main/java/com/cruisetune/player/steering/OneOsContract.kt)，负责服务发现、监听注册、回调解析和菜单查询。

客户端直接使用 Android Binder／Parcel。参考代码中的注册包装名和 `getControlIndex` 日志不是厂商 Java SDK 的方法声明，不能据此增加同名反射方法的加载前提。服务端的权限、服务编号和菜单含义仍需按目标固件确认。

播放器将按键交给自己的播放服务，无需枚举其他应用的媒体会话。参考应用的通知访问、日志补充采集、功能授权和原生初始化不属于当前接入依赖；第三方 APK、DEX、SO 和反编译源码不随项目提交。

当前明确采用以下客户端协议配置：

1. 显式绑定系统 OneOS 服务 `com.geely.service.oneosapi/com.geely.service.oneosapi.OneOSApiService`，验证系统包或 system UID 身份。
2. 只接受根接口 `com.geely.lib.oneosapi.IServiceManager` 或输入接口 `com.geely.lib.oneosapi.input.IInputManager`。根接口只调用已恢复 SDK 中的 `getService` 事务 2；按参考客户端两条发现路径出现过的候选服务 ID 查找，严格匹配输入 descriptor，记录查询结果。不扫描事务 1～5，不向可能为 addService 的事务写入探测数据。
3. 在匹配的输入 Binder 上按样本 DEX 核对的顺序写入：接口令牌、监听 Binder、tag、四个媒体来源键码，以事务 3、flags 0 提交。无异常只表示请求已提交；界面明确等待真实事件，不将其当作按键已验证。附加返回数据不擅自解释为 boolean 成败。
4. 回调接口为 `com.geely.lib.oneosapi.input.IInputListener`。事务 1 读取三个整数，事务 2～6 读取两个整数，分别表示原始、短按、长按开始／结束／触发、原生双击。校验接口令牌和数据长度，保留附加整数用于诊断。
5. 监听 Binder 仅传给上述已核验的输入端点，不通过公共组件发布。允许该端点委托子服务回调，不再假定回调 UID 必须等于根服务 UID；实际 UID 会进入诊断。回调只能转为预设媒体键／动作，未知键仅记录。
6. 菜单使用样本中的事务 5 读取一个整数；2 作为该协议配置的媒体菜单，其他值和读取失败均禁止 OneOS 映射执行。此数值含义仍需与真实固件核对，不从失败推断为媒体。

这些是已核对的**客户端字段布局**，不是厂商公开的跨固件 API 保证。车机接口不匹配时显示诊断，不试探其他注册、发键或注销事务。原车 QQ 音乐是否同时处理相同按键、该固件是否使用相同编号，仍需实车确认。

## 回调生命周期

厂商连接运行在本应用私有的 `:steering` 进程，由播放服务绑定一个不导出的辅助服务。两个本应用进程之间使用项目自己定义的 AIDL；它不依赖厂商 Java SDK。辅助进程不初始化曲库、缓存或账号组件。

参考样本的注销包装只清本地字段，无法证明远端注销协议。因此关闭、主动重连、连接异常需要重建时，先停止本地事件投递并解绑，再结束独立按键进程，使持有的回调 Binder 失效；不会终止音乐播放进程，也不猜测注销事务。远端如何清理死 Binder 的内部记录仍由车机服务实现决定。

绑定或远端暂时异常由主进程按 4、8、16、30 秒退避重建；缺少服务、身份／权限不符或协议不匹配给出明确结果。远端调用放到工作线程，同步 Binder 调用无法靠协程强行中断，关闭辅助进程可释放客户端阻塞调用。旧代次的回调和排队命令不会进入新的连接。

## 两路按键与手势策略

- 标准媒体键保持原有 Media3 路径；注册请求成功本身不会使应用拦截标准键。
- 若两种来源都到达，在 350ms 关联窗口内由先到的有效路径处理。OneOS 已获得该次按键时抑制重复标准按下／抬起；标准路径先处理时，不再执行紧随的 OneOS 映射。使用按键、设备和 downTime 配对标准按下／抬起，不拦截音量等无关键。
- 自定义映射适用于 OneOS 承接的事件；双路事件的实际顺序和间隔仍需实车核对，不能把时间关联当作所有固件通用的物理事件 ID。
- OneOS 短按间隔小于 80ms 时去重，350ms 窗口识别双击。长按开始／触发合并为一次，松手后 300ms 抑制短按。原始事件只记录，原生双击不作为第二条执行路径。
- OneOS 事件接收和映射执行前都读取菜单；菜单变化取消待处理手势。诊断观察独立于菜单／映射门控。超过 1 秒才处理的事件会记录过期原因，避免延迟操作。
- 映射定向进入已有播放服务，保留缓存读取、报错后切歌恢复、暂停意图、熄屏、通话及音频焦点保护。不枚举其他播放器，不发送全局厂商按键注入命令。

## 设备检查

在目标车机上按以下顺序检查；服务注册成功仅表示请求已提交，实际按键事件应出现在诊断记录中。

1. 开启诊断模式，确认 OneOS 服务绑定、输入接口及注册结果。
2. 切到媒体菜单，分别按播放、左、右键，检查来源码、回调参数与菜单值。
3. 关闭诊断模式，检查单击、双击、长按松手是否各执行一次；切换菜单后不执行媒体映射。
4. 检查原车 QQ 音乐是否同时响应，以及导航、通话、语音助手和休眠唤醒后的音频焦点与重连。
5. 网络或授权错误后切到完整缓存歌曲，确认播放恢复；熄屏保持暂停，亮屏后由用户继续。

反馈时提供复制的诊断信息与按键顺序。自动化与模拟器操作方法见 [测试指南](../android-app/TESTING.md)。
