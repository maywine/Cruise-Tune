# Cruise Tune 0.5.9 界面与动效审查

审查依据：apple-design 的反馈、信息层级、可预测性、可访问性原则，以及 animate 的“频率 → 目的 → 实现 → 中断 → 减少动态效果”判断顺序。将这些原则用于 Android 原生界面，不机械套用 Web/CSS 实现。

范围：当前工作区 UI 代码、已安装的 0.5.9、BlueStacks Android 13 实屏。检查原始竖屏、360×640 窄窗口、640×360 横屏、横屏 1.6 倍字体，以及来源和移除确认框。尺寸为按显示密度换算的名义 dp，实际布局还扣除系统栏。最初只做审查；后续 0.5.10 修复与复验见文末，以上审查结论描述的是 0.5.9。

## 需修复的问题

### 1. [P1] 紧凑横屏隐藏了错误和缓冲状态

位置：[MainActivity.kt](../android-app/app/src/main/java/com/cruisetune/player/ui/MainActivity.kt#L182-L193)、[PlayerLayoutSpec.kt](../android-app/app/src/main/java/com/cruisetune/player/ui/PlayerLayoutSpec.kt#L7-L11)。

`banner` 只在非 compact 布局加入界面。640×360 横屏实屏确认没有状态行；大字体时连格式/缓存状态也被隐藏。此时即使后台更新文件大小限制、重新登录原因或缓冲信息，用户也只能看到“重试／重新连接”按钮，无法理解为何停播。

这违背状态反馈和“理解当前发生什么”的原则。空间紧张时应先减少封面、品牌副标题及装饰间距，保留至少一行可读的状态。错误应能查看完整原因，不能仅用一行省略号截掉关键行动信息。

验收：640×360、853×480，分别在普通和大字体下验证正在缓冲、登录失效、文件受限三种状态；原因和主要操作同时可见。此次实屏验证的是状态行被隐藏，没有为了复现错误去破坏有效授权。

### 2. [P2] 移除操作过于接近常用操作，确认框正文偏小

位置：[MainActivity.kt 来源操作](../android-app/app/src/main/java/com/cruisetune/player/ui/MainActivity.kt#L350-L368)、[确认框](../android-app/app/src/main/java/com/cruisetune/player/ui/MainActivity.kt#L407-L410)、[Design.kt](../android-app/app/src/main/java/com/cruisetune/player/ui/Design.kt#L55-L63)。

来源列表把“打开目录”和“移除目录”作为相邻的大型同色按钮展示。确认框又直接使用系统默认标题/正文样式，`styleDialog` 只统一按钮文字和最小高度；实屏中作用范围说明明显小于车机其他面板的正文。取消和移除使用同一强调色，缺少清晰的危险操作层级。

建议将移除收进来源详情或管理区；确认框统一车机文字与触摸规格（正文约 20sp、标题 24sp、按钮至少沿用 76dp 的主要控件规范），为移除使用明确的语义样式，保持取消容易识别。不需要给确认框增加弹跳来强调风险。

验收：普通、大字体及日/夜模式下，完整看清本机曲库、队列和离线缓存的影响范围；取消与移除有明确区分。此次仅打开并取消确认框，没有执行删除。

### 3. [P2] 窄竖屏的播放器卡片挤占了列表空间

位置：[PlayerLayoutSpec.kt](../android-app/app/src/main/java/com/cruisetune/player/ui/PlayerLayoutSpec.kt#L7-L11)、[MainActivity.kt 播放卡片](../android-app/app/src/main/java/com/cruisetune/player/ui/MainActivity.kt#L180-L231)。

compact 主要根据高度是否小于 600dp 判断。名义 360×640 窗口仍使用较大的品牌区、歌曲信息及进度区，实屏歌曲列表不足以完整显示一行，品牌标题也被截断。这是响应式分配问题，不能靠缩小所有文字解决。

建议根据扣除系统栏后的剩余列表空间选择布局，给列表预留明确的最小可用高度，再决定是否显示副标题、封面尺寸和状态间距。紧凑化时仍须保留第 1 项中的关键状态。

验收：360×640 和小多窗口场景中至少完整显示一首歌曲并能继续滚动；主播放操作不被挤出屏幕。这一项主要影响窄窗口，不能直接推断实际车机也采用此尺寸。

### 4. [P2] 小屏下循环模式是盲切，缺少当前状态

位置：[MainActivity.kt](../android-app/app/src/main/java/com/cruisetune/player/ui/MainActivity.kt#L618-L619)、[PlayerLayoutSpec.kt](../android-app/app/src/main/java/com/cruisetune/player/ui/PlayerLayoutSpec.kt#L10-L11)。

设置中的“切换顺序／单曲／列表循环”不显示当前值，点击后按顺序加一并立即关闭面板。紧凑屏幕不显示底部模式按钮，因此用户无法直接确认现在是哪一种状态，可能需要反复进入设置试探。

建议使用明确的单选项并标记当前状态；选择后立即反馈，在紧凑主界面保留简短的当前模式标识。使用即时选中反馈，不给这种高频设置增加位置或缩放动画。

验收：从任意初始模式进入设置，都能一次直接选中想要的模式，并在关闭面板后确认结果。此项由代码核对得出，审查期间没有切换用户的播放模式。

### 5. [P2] 高频进度刷新与同步缓存查询耦合

位置：[MainActivity.kt 500ms 刷新](../android-app/app/src/main/java/com/cruisetune/player/ui/MainActivity.kt#L146-L150)、[状态读取](../android-app/app/src/main/java/com/cruisetune/player/ui/MainActivity.kt#L280-L305)、[MediaCache.kt](../android-app/app/src/main/java/com/cruisetune/player/playback/MediaCache.kt#L61-L70)。

主线程每 500ms 执行整段 `renderPlayer()`，其中缓存状态会同步调用下载索引查询。播放时间和进度本来是便宜的连续数据，不应与磁盘相关查询绑在一起。磁盘繁忙时会增加触摸与绘制延迟风险；这个结构也不适合直接提高整段刷新的频率来让进度更顺滑。

建议把缓存状态通过后台计算和下载/缓存事件更新到 UI；播放进度单独读取控制器时间。若要平滑进度，按 animate 对连续进度的建议使用线性更新，拖动时保持 1:1，松手/切歌时立即同步真实位置，不用 spring 或逐次 ease-out 追赶旧数值。

验收：缓存、预缓存或离线任务活动时采集主线程帧耗时，确认进度刷新没有同步数据库调用；拖动进度时不被定时器抢回。当前证据是代码结构风险，并未证明之前的声音断续由此引起。

## 应保留的设计

- 播放、切歌、列表选择的触下反馈即时，不叠加缩放和入场动画。按 animate 的频率判断，这些高频操作不应为了装饰增加动效。
- 进度条拖动时立即显示目标时间，并暂停定时器覆盖该手势；这是正确的直接操控方向。
- RecyclerView 使用原生滚动，禁用列表条目入退场动画，符合车机阅读稳定性要求。
- 减少动态效果同时参考应用设置与系统 Animator 配置；开关采用原生反馈并提供即时状态方式。
- 主播放按钮有明确强调，深色背景和文字层级整体清晰。现阶段不建议添加唱片旋转、标题跑马灯、歌曲列表 stagger 或弹跳按钮。

## 后续非阻断建议

播放队列保留完整顺序，用户滚动位置也会被保留。播放持续前进或切到短横屏后，当前歌曲可能离开可视区；可考虑增加“定位当前歌曲”入口，而不是强制自动滚动打断用户浏览。选中标签和播放主按钮也可适当区分视觉权重。

## 验证边界与环境恢复

本轮是代码和交互审查，不是完整性能测试，没有修改播放逻辑、账号、曲库或缓存。尺寸、密度、字体比例和旋转设置已逐项核对恢复；保持用户原本的播放状态。未进行实车、TalkBack 语音或逐帧动效录制验收。原始截图仅保存在本地忽略目录，文档不包含个人曲目、账号或凭证。


## 0.5.10 修复与复验

上述五项已实施：

1. 紧凑布局将状态移到顶部，提供信息图标及可点击的完整详情；普通布局继续在播放卡片显示。大字体时优先保留状态与主要操作。
2. 来源移除收进“管理”，确认框明确读取方式与本机数据影响，正文 20sp、标题 24sp、按钮至少 76dp；移除使用危险色，取消使用普通文字色。
3. 竖屏根据字体与预计内容高度选择紧凑布局，给歌曲列表预留空间。360×640 实屏普通字体与 1.6 倍字体均可完整看到至少两行歌曲。
4. 播放顺序改为标记当前值的单选列表，支持一次选择目标模式；设置标签与紧凑主界面同步显示结果。
5. 缓存状态改为后台每秒读取，按歌曲缓存标识切换任务，取消旧任务并过滤旧结果；进度单独按屏幕帧读取真实播放位置，拖动期间不覆盖用户输入。播放事件和会话附加状态变化负责更新其他信息。没有给高频操作增加装饰动画。

123 项主机自动化测试、Release 构建与 lintRelease 通过。新增覆盖紧凑状态详情、大小字体布局、确认框尺寸及危险色、模式直接选择，以及后台查询线程、切歌取消和查询失败状态。

BlueStacks Android 13 实际覆盖安装 0.5.10，保留网页登录及 160 首曲库。实屏验证普通竖屏、360×640 竖屏（1.0/1.6 倍字体）、640×360 横屏（1.0/1.6 倍字体），状态详情、模式选择并恢复、目录管理与移除确认后取消；继续播放、自动切歌、拖动后继续推进及暂停正常。未执行目录删除或重新授权。

本轮短时绘制采样 2,156 帧，系统报告 janky frames 71（3.29%），P50/P90/P95/P99 为 6/15/23/57 ms；采样包含切歌、封面更新及拖动，不是与旧版同负载的性能对照，不能据此宣称声音卡顿已解决或始终稳定满帧。后台查询线程已由自动化验证；尚未做持续下载压力下的主线程追踪、全部日夜主题弹窗组合、TalkBack 语音、实车测试。未人为使有效账号失效，长错误详情由自动化验证。

显示尺寸、密度、字体与旋转设置已逐项恢复；深色主题及顺序播放保持原值，测试结束暂停。原始截图和绘制数据仅保存在忽略目录。交付 APK 与实际安装包一致，校验见 TESTING.md。
